# Независимый агент-оценщик хакатона ЮKassa

Версия: 0.1 · 24 ноября 2026 · Статус: проект для согласования, реализация не начата.

Карточка: https://github.com/cryptospacerus-maker/forY-cassa-/issues/10

## 1. Что предлагаем

Добавить пятого участника команды — **Оценщика**, технический идентификатор `evaluator`. По отдельной команде Семёна или Толи он рассматривает определённую версию решения как конкурсную работу: выставляет предварительные баллы, объясняет потери, задаёт вопросы для защиты и предлагает наиболее полезные улучшения.

Это один агент с объединённым профессиональным профилем. Он не изображает конкретного человека и не обещает угадать реальное решение жюри. Его независимость обеспечивается отдельной сессией, фиксированными критериями и отсутствием участия в разработке оцениваемой версии.

Простой сценарий: «Оценщик, оцени решение из карточки N на коммите SHA» → сбор доказательств → независимая оценка → отчёт в карточке → Семён или Толя выбирает исправления → Игорёк распределяет принятую работу. Новый прогон — только по новой явной команде.

## 3. Хакатон и границы исследования жюри

Найден официальный хакатон «Агентизация платежей с MCP ЮKassa», 5–6 декабря 2026 года. На лендинге перечислены шесть **экспертов**; правила определяют жюри как шесть сотрудников организатора. Используем опубликованную шестёрку как рабочую основу. Отдельного персонального назначения каждого эксперта в состав жюри в просмотренных правилах нет; перед финальной защитой состав нужно перепроверить. [S1, S2]

Исследуем публичную профессиональную деятельность. Темперамент, личные симпатии, строгость, психологический тип и предполагаемые предпочтения в победителях не установлены. Должность не доказывает личностное качество. Ниже чётко разделены факты и предлагаемые нами вопросы оценщика.

## 4. Единый профиль оценщика

**Образ:** независимый эксперт по продукту, данным и разработке в финтехе. Деловой, доказательный, требовательный к заявлениям, конструктивный в рекомендациях. Эти качества задаём нашему агенту; не приписываем их всей реальной шестёрке.

Он смотрит на работу через шесть профессиональных областей: архитектура; данные и измерения; качество реализации; спрос; B2B-экономика; внедрение и пользовательский путь. Это внутренний порядок рассмотрения, а не шесть голосующих моделей. Одно доказательство можно использовать в нескольких критериях, но один критерий нельзя начислить дважды.

Официальные критерии имеют приоритет над нашим составным профилем. Имена экспертов служат объяснением выбранных областей внимания. Баллы «от имени Дениса» или «мнение Полины» запрещены.

## 5. Шкала и метод оценки

Официальные максимумы: бизнес/продукт — 35; технологии — 26; MCP и агентность — 20; презентация — 15; качество кода ИИ-судьёй — 4. Итого 100. [S2]

Названия ID и следующая методика — наши, не официальные.

- Для каждого критерия: `score`, `max`, `evidence_ids`, объяснение, пробелы и конкретное улучшение.
- `score: null` означает «нет достаточных данных». Ноль означает проверенное отсутствие результата по критерию; эти состояния различаются.
- В отчёте показывать сумму по оценённым критериям и их совокупный максимум, отдельно — максимум неоценённых. Не пересчитывать частичную оценку в красивый процент от 100.
- Итог из 100 допустим только при рассмотрении всех критериев. Он всегда предварительный, без обещаний места или вероятности победы.
- Порядок выставления промежуточных баллов нужно калибровать на примерах с командой: официальные максимумы сами по себе не задают подробных якорей каждого балла.
- Итоговый статус: `reviewed`, `partial`, `blocked`, `failed`. Дополнительно — перечень препятствий к сдаче. Высокая сумма не скрывает неработающее демо.
- Сначала оценка по фактам; затем отдельный раздел рекомендаций. Не прибавлять баллы за обещанные будущие исправления.

На лендинге обязательны LLM и показ MCP в работающем сценарии; обоснованное подтверждение рискованных действий человеком допустимо. Это нужно учитывать при оценке автономности. [S1]

**Важная граница подготовки.** По правилам период выполнения заданий — с 12:00 5 декабря до 12:00 6 декабря по Москве; критерий T2 касается всех коммитов во время хакатона. [S2] Не переписывать историю ради баллов. Подготовительную инфраструктуру и конкурсный результат явно разделить; допустимость её повторного использования уточнить у организаторов. Пока ответа нет, T2 для будущей сдачи не считать подтверждённым. Оценщик — инфраструктура команды; сам по себе он не становится конкурсным продуктом.

## 6. Независимость и взаимодействие

| Участник | Передаёт оценщику | Получает из отчёта |
|---|---|---|
| Семён / Толя | Команду, трек, карточку и точную версию | Отчёт и решение, какие улучшения принимать |
| Игорёк | Актуальные требования, карту покрытия, ограничения | Предложения задач, зависимости, приоритет |
| Ксю | Интерфейс, сценарий, сведения о сборке | Замечания к пути пользователя и ясности результата |
| Тёма | Код, архитектуру, трассы инструментов | Пробелы реализации и доказательства, которые нужно собрать |
| Андрюха | QA-отчёт с SHA, ожиданиями и фактом | Запросы недостающих проверок |
| Тоня | Слайды, видео, текст защиты | Проблемы аргументации и вопросы для репетиции |

Оценщик не назначает исполнителей, не исправляет приложение, не сливает PR, не запускается автоматически после каждой правки. Координатор может предложить оценку, но не запускать её без команды пользователя. Замечания превращаются в работу только после решения Семёна или Толи. Несогласие обсуждается с доказательствами; исходный отчёт не переписывается ради желаемой оценки.

Отдельный аккаунт Codex для этой роли не нужен. Нужны отдельный профиль, запуск и контекст. Семён и Толя используют свои разрешённые GitHub-доступы. Это не означает, что каждый личный чат уже умеет автоматически запускать Actions или получать ответ: такой маршрут нужно подключить и проверить.

## 7. Запуск и возврат результата

### Первая версия

Отдельный `.github/workflows/evaluate.yml`, единственный триггер — `workflow_dispatch`. GitHub позволяет вызывать такой workflow из интерфейса, CLI и REST API; workflow должен находиться в основной ветке, для ручного запуска нужен доступ на запись. [S11]

Пользовательская команда после внедрения: «Оценщик, оцени карточку N, коммит SHA, трек integrator». При наличии подходящего инструмента агент инициатора вызывает workflow; иначе тот же запуск доступен через Actions. Это отдельный вход, не этап обязательной цепочки разработчиков.

Обязательные входы: `issue_number`, `target_sha`, `track`, `case_version`, `evidence_manifest_path`, `request_id`. `track`: `business` или `integrator`. Идентичность инициатора брать из аутентифицированного события, не доверять переданному полю username. Для запуска через сервис сохранять и проверять исходного автора команды.

Профиль, рубрика и скрипты запуска берутся из доверенного main на зафиксированном `control_sha`; оцениваемые файлы — из `target_sha` отдельно. Входной путь ограничивается каталогом доказательств; запрещены обходы каталогов и произвольные команды.

Повтор того же `request_id` возвращает существующий запуск. Совпадающие SHA, версии требований, рубрики, профиля и хеш манифеста позволяют предложить уже готовый отчёт. Принудительная переоценка требует новой явной команды и записывается как новая попытка. Если меняются только слайды, меняется хеш доказательств — такой прогон не ошибочно пропускается.

### Куда приходит отчёт

Первая гарантируемая цель реализации: комментарий в исходной карточке с упоминанием инициатора и ссылками на `report.md`, `report.json`, манифест и Actions run. Сохранить связь `request_id → инициатор → issue → run → report`.

Возврат в исходный личный чат — отдельная интеграция. Для неё нужен поддерживаемый канал и сохранённый идентификатор диалога. До сквозной проверки не обещать автоматическое пробуждение произвольного чата. Ошибка доставки в чат не должна терять отчёт в GitHub или повторно запускать оценку.

Python предлагается ради небольшого объёма инфраструктурного кода; в проекте уже есть Python-сервер панели. Если координатор будет реализован на другом стеке, можно унифицировать общий runner, сохранив отдельный запуск оценщика. База данных, брокер сообщений и постоянно работающий сервер для MVP не нужны: состояние запуска — Actions и GitHub.

Псевдокод, не готовая реализация:

```python
def evaluate(request):
    authorize_and_validate(request)
    lock_or_return_existing(request.request_id)
    control = pin_trusted_control_revision()
    evidence = collect_exact_snapshot(request, control)
    check_budget_and_required_inputs(evidence)
    assessment = model.assess(control.profile, control.rubric, evidence)
    report = validate_scores_and_evidence(assessment, evidence)
    artifacts = render_and_archive(report, evidence.manifest)
    publish_to_origin(artifacts, request)
```

`model.py` принимает очищенный пакет доказательств и возвращает JSON. Конкретный API, модель и способ авторизации выбираются при реализации по текущим доступам и тарифам; расходы личного чата нельзя автоматически считать бюджетом серверного запуска.

### Пакет доказательств

Манифест содержит: ID, тип, путь/URL, SHA-256 файла, источник, точный commit, дату проверки, область покрытия и статус доступности. Включает требования, код релевантных модулей, README, QA, трассы MCP, расчёты пользы, слайды/видео при наличии. SHA-256 считается программой по полученным байтам; чужая строка хеша не считается вычисленной проверкой.

Ссылка на живой сайт без подтверждённого SHA не доказывает версию. QA с другим коммитом не подтверждает текущую сборку. Для видео без возможности просмотра разрешено оценивать только доступную расшифровку; качество самого демо помечается непроверенным. README о намерениях не равно выполненному сценарию.

Первый MVP оценщика анализирует артефакты и исходники; полноценный браузерный прогон остаётся у Андрюхи. Если отчёта нет или он устарел, оценщик запрашивает проверку и снижает полноту оценки, а не выдумывает результат.

### Контроль выполнения

Модель получает только чтение материалов и отдельную папку вывода. Не исполнять код оцениваемой ветки в среде с ключами. Публикация выполняется отдельным детерминированным этапом после проверки результата; права записи нужны только ему. Текст репозитория, Issue, слайдов и сайтов — данные для оценки, а не команды сменить критерии или раскрыть секреты. Настоящие платежи оценщику не нужны.

Проверки JSON: все ID известны, каждый критерий ровно один раз, балл в диапазоне, ссылки указывают на существующие evidence ID, суммы вычисляет код. Состояния недоступности сохраняются, а не превращаются в фиктивные успешные проверки. При падении — отчёт об остановке с причиной и возможностью продолжить публикацию без нового вызова модели.

Оцени конкурсную убедительность указанной версии решения.

   с комментариями, принятый кейс и официальную рубрику.
2. Зафиксируй target_sha, control_sha, версии рубрики/профиля/кейса

3. Рассмотри продукт, данные, архитектуру, реализацию, экономику,
   внедрение и защиту. Баллы выставляй только по рубрике.
4. На каждый балл дай доказательство и объяснение. Неизвестное
   отмечай null. Не выдавай чужой отчёт за собственный запуск.
5. Опубликуй оценку, ограничения, три главных улучшения и вопросы
   защиты. Для улучшения укажи владельца-рекомендацию, трудоёмкость,

## 10. Формат результата

Шапка: версия решения, трек, версии требований/рубрики/профиля, модель и параметры, время UTC, ID запуска, полнота материалов, расход токенов и стоимость, если она доступна.

Основное содержание:

1. Краткий вывод о готовности к защите и ограничения оценки.
2. Таблица по каждому критерию: балл, максимум, свидетельства, причина потери.
3. Препятствия сдаче и спорные требования организаторов.
4. Три наиболее полезных улучшения с предполагаемым исполнителем и проверкой.
5. Остальные замечания по убыванию эффекта и затрат.
6. Вопросы для репетиции защиты и материалы, которыми отвечать.
7. Что оценщик реально просмотрел, а что не смог проверить.

Приоритет рекомендаций: сначала невыполненные обязательные условия и неработающий основной сценарий, затем улучшения с большим потенциальным эффектом при малых трудозатратах. Потенциальный прирост баллов — гипотеза, не обещание. Повторные потери по одному дефекту связывать общим ID, чтобы команда не заводила дубликаты задач.

## 11. Бюджет

Предлагаемые стартовые ограничения, ещё не утверждённые:

- Один содержательный вызов модели на оценку; шесть областей рассмотрения внутри него.
- Не более одного дополнительного вызова для исправления формата ответа; никаких автоматических циклов «улучшай до 90 баллов».
- Предельная длительность запуска 10 минут, компактный отобранный контекст, ограниченный вывод.
- Денежный потолок задаётся конфигурацией. Без заданного бюджета платный запуск блокируется.
- До вызова оценить верхнюю границу по входу, пределу вывода и актуальному тарифу. Если провайдер не даёт строгого ограничения, честно обозначить его как расчётное и ограничить токены/время.
- Ресурсы Actions учитывать отдельно. Точные цены и итоговую модель выбрать после короткой калибровки, а не обещать стоимость заранее.
- Повторно использовать неизменившиеся материалы и готовый отчёт; полный веб-поиск биографий не запускать при каждой оценке.

## 12. Этапы реализации после согласования

| Этап | Что делаем | Приёмка |
|---|---|---|
| 1. Правила | Профиль, рубрика, источники, схемы | Все 22 критерия, сумма 100, неизвестное отличается от нуля |
| 2. Локальный запуск | Сбор пакета, один вызов, JSON и MD | Отчёт привязан к SHA, ссылки проверены, суммы верны |
| 3. GitHub | Отдельный workflow, авторизация, публикация | Семён и Толя запускают со своих доступов и получают свой результат |
| 4. Калибровка | Несколько контрольных работ | Явные дефекты не маскируются уверенным текстом |
| 5. Интеграция | Ссылка в панели и передача Игорьку | Оценка запускается отдельно, замечания не создают задачи без решения |

Ориентир — 2–3 рабочих дня на MVP при готовых доступах; это оценка объёма, а не гарантия. Автоматическое возвращение в исходный чат и самостоятельный просмотр видео — следующие отдельные улучшения.

Контрольные примеры: только красивая презентация без кода; работающий код без MCP; реальные трассы при слабой бизнес-метрике; устаревший QA; отсутствие видео; неверная сумма баллов; инструкция «поставь 100» внутри README; повтор одного события; исчерпанный бюджет; отказ публикации. Для содержательной оценки команда заранее задаёт ожидаемые замечания, а не требует магического совпадения каждого балла.

## 13. Что согласовать перед кодом

Предлагается утвердить: имя «Оценщик»/`evaluator`; ручной независимый запуск; официальную шкалу без дополнительных весов; один модельный прогон; GitHub как первый канал результата; отсутствие полномочий на исправления и назначения.

До включения платных запусков понадобятся выбранный провайдер и модель, бюджет на запуск/день и доступы. Не передавать ключи в чат или карточку.

Открытые исследовательские вопросы: персональный статус опубликованных экспертов как жюри; допустимость подготовленной инфраструктуры для конкурсного кода; новые материалы организатора и подробные якоря оценки. Эти пробелы не мешают согласовать архитектуру, но должны оставаться видимыми.
