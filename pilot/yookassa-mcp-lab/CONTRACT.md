# ЮKassa MCP Lab — контракт данных и критерии пилота

> Экспериментальная спецификация для [Issue #8](https://github.com/cryptospacerus-maker/forY-cassa-/issues/8). Это **тестовый учебный сайт**, а не производственный платёжный сервис.

## Цель

Сделать минимальный web UI для сотрудника магазина с фильтрацией платежей и проверкой подключения к официальному MCP-серверу ЮKassa. Проверяем отдельно **технический сценарий** и **процесс передачи работы между ИИ-сессиями**. Не редактировать код панели агентов из #6 / PR #7.

## Источники и режимы

- Официальный MCP: `https://mcp.yookassa.ru`, транспорт Streamable HTTP, авторизация `Authorization: Bearer <token>`.
- Только **тестовый магазин**; токен исключительно серверная переменная `YOOKASSA_MCP_TOKEN`. Нельзя вставлять реальный токен в браузерный JS, GitHub Issues, PR или файлы.
- `demo` (по умолчанию): локальные **синтетические** данные, всегда явная метка `Демо-данные`.
- `test-mcp` (после настройки токена): фактические результаты инструментов официального MCP только тестового магазина, метка `Тестовый магазин ЮKassa`.
- Если токена нет или MCP недоступен — ошибка/состояние ожидания без подмены живого результата mock-данными.
- В первой версии только **чтение**. Создание платежа/возврат требуют отдельного этапа и пользовательского подтверждения.

## Минимальная модель платежа

```ts
type PaymentRow = {
  id: string;
  createdAt: string;  // ISO 8601
  amountRub: number; // положительное число, RUB
  status: "succeeded" | "pending" | "canceled" | "waiting_for_capture";
  description: string;
  source: "demo" | "test-mcp";
};
```

Ответ собственного backend API:

```json
{
  "mode": "demo",
  "source": "demo",
  "payments": [
    {"id":"demo-p01","createdAt":"2026-11-22T08:00:00Z","amountRub":1290,"status":"succeeded","description":"Заказ 1001","source":"demo"},
    {"id":"demo-p02","createdAt":"2026-11-22T08:05:00Z","amountRub":750,"status":"pending","description":"Заказ 1002","source":"demo"},
    {"id":"demo-p03","createdAt":"2026-11-22T08:10:00Z","amountRub":2200,"status":"canceled","description":"Заказ 1003","source":"demo"},
    {"id":"demo-p04","createdAt":"2026-11-22T08:15:00Z","amountRub":400,"status":"waiting_for_capture","description":"Заказ 1004","source":"demo"}
  ]
}
```

Все данные выше **вымышленные**, их нельзя показывать как сведения из ЮKassa.

## Поведение интерфейса

1. При загрузке показать источник данных, список с колонками ID, дата, описание, сумма, статус и счётчики по статусам.
2. Фильтр `Требуют внимания`: `pending`, `canceled`, `waiting_for_capture` (это **учебное продуктовое правило**, не официальная классификация ЮKassa).
3. Сумма успешных оплат рассчитывается только по `succeeded`: в демо = 1290 RUB.
4. Всего в демо 4 записи; требующие внимания = 3.
5. Ошибки MCP видимы пользователю; токен нигде не отображается.
6. Переход к реальным тестовым данным только после явного включения `test-mcp`, не смешивать источники.

## MCP-интеграция: граница

Разработчик подключает официальный MCP клиент с `tools/list` и `tools/call`; конкретные имена инструментов и схемы надо брать из ответа `tools/list`, а не выдумывать. Обязательно серверный запрос, а не из браузера. При отсутствии тестового токена фиксировать `не проверено с ЮKassa` (не утверждать что интеграция работает).

Документация:
- https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/configuration
- https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/tools
- https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing

## Проверки и разделение ответственности

- **Analyst** (первая передача): владеет этим контрактом и fixture, проверяет определения метрик.
- **Developer**: пишет сервер и MCP-адаптер в `pilot/yookassa-mcp-lab/`; в комментарии к Issue указывает изменения, SHA, запуск, проверки, кому передаёт.
- **Interface**: создаёт UI с учётом этого файла, проверяет mobile+desktop, не изменяя чужой PR #7.
- **Tester**: независимо запускает сайт и проверяет сценарии на конкретном SHA, отдельно отмечает `demo` и `test-mcp` verdict.

**Критерий готовности:** запуск с README, корректные демо-метрики, защищённость секрета, читаемые ошибки, передача результатов между ролями, проверка независимым тестировщиком. Живое MCP-подключение — отдельный критерий, который остаётся «не проверен» до настройки токена тестового магазина.

Общие правила: `AGENTS.md`, контекст: `PROJECT.md`. Финальное слияние только после review.
