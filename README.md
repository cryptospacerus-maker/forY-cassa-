# Хакатон ЮКассы · План автономной команды агентов

Семён или Толя формулирует одну задачу со своего аккаунта. Команда агентов читает актуальное состояние проекта, выбирает нужные роли, распределяет работу и возвращает один проверенный результат. Семён и Толя отвечают за разработку, Тоня — за презентацию и запись согласованного пилота в бизнесе.

**Текущее состояние.** Сессии A и B уже читают общий репозиторий и пишут в карточки. Правила сверки действуют. Ближайшая проверка — применить изменение из A в начатом черновике B. Профили, автоматический запуск и сборка результатов описаны ниже как план реализации. Проверку доступа C и D команда отложила.

## 1. Закончить проверку общего контекста

Перед каждым запросом по проекту сессия открывает [AGENTS.md](AGENTS.md) и [PROJECT.md](PROJECT.md) из main, проверяет изменения в карточках, комментариях, PR и коммитах после предыдущей сверки. Подробно читает материалы, влияющие на задачу. После содержательной работы сохраняет решение, результат проверки, ссылку на версию и следующий шаг. Нужная другим агентам информация из личного чата становится общей после записи в GitHub.

**Что сделать сейчас.** Толя сохраняет первую сводку в [задаче B](https://github.com/cryptospacerus-maker/forY-cassa-/issues/3). Затем Семён через [задачу A](https://github.com/cryptospacerus-maker/forY-cassa-/issues/2) фиксирует одно изменение в PROJECT.md. Толя пишет в прежнем чате «Продолжи задачу № 3». Шаг пройден, когда B самостоятельно находит изменение, обновляет файл и оставляет ссылки на источник и новую версию. Сравните обе версии.

## 2. Описать профессии агентов

Семён и Толя добавляют в папку `agents/` по одному короткому файлу на профиль. Каждый файл определяет, когда нужен агент, какие материалы он читает, что может менять и как проверяет результат. Роль можно запускать из общего сервиса независимо от аккаунта автора запроса.

| Профиль | За что отвечает | Что передаёт дальше |
|---|---|---|
| Координатор | Определяет цель, зависимости, доступные роли и критерий приёмки. Следит за общей версией | План работ и финальный результат с проверками |
| Бизнес-аналитик | Разбирает процесс магазина, потребность сотрудника и границы сценария | Пример входа, ожидаемый выход и критерий пользы для бизнеса |
| Разработчик агента и интеграций | Реализует логику, вызовы инструментов и обработку ошибок. Для сценария с ЮКассой проверяет выбранную интеграцию в тестовой среде | Код, команды запуска и результаты собственных проверок |
| Разработчик интерфейса | Если нужен экран, делает путь пользователя от запроса до результата по согласованному формату данных | Рабочий интерфейс и пример для демонстрации Тоне |
| Тестировщик | Независимо проходит сценарий на собранной версии, проверяет ошибки и повторные действия | Версия, примеры, ожидаемый и фактический результат, замечания для исправления |

**Проверка.** По запросу «Объясни причины расхождения в отчёте» координатор может выбрать аналитика и проверяющего. По запросу «Собери экран со сводкой» — подключить разработчиков. Число ролей и число аккаунтов могут различаться.

## 3. Сделать запуск по одной команде

Предлагаемый первый вариант — одна главная карточка GitHub Issue, событие запуска в GitHub Actions и программа-координатор, которая вызывает модель через API с нужными профилями. Из любого подключённого аккаунта участник просит создать такую карточку с целью и ожидаемым результатом. После явной команды запуска программа сама вызывает исполнителей. GitHub хранит общую историю. Запуски через API требуют отдельно настроенного доступа и бюджета. Лимиты личных чатов в расчёт этого бюджета не включаем.

**Порядок реализации.** Начать с двух профилей — исполнитель и проверяющий. Настроить запуск только по командам участников команды, хранить ключ в секретах среды и задать предел расходов и попыток. Сохранять идентификатор запуска в главной карточке. При повторной доставке того же события продолжать существующий запуск. После успешного прогона подключить остальные роли.

**Проверка.** Участник отправляет одну команду. В карточке появляются результаты двух разных запусков ролей и итог проверки. Второму участнику достаточно открыть ссылку, чтобы увидеть ход работы.

## 4. Автоматизировать распределение и согласование

Координатор читает запрос и историю проекта. Он выделяет подзадачи и для каждой записывает результат, зависимости, область изменений и критерий готовности. Агент соответствующего профиля оценивает задачу и предлагает способ решения. Координатор закрепляет за подзадачей одного исполнителя и запускает независимые работы параллельно. Для текущей ручной репетиции владельцев по-прежнему назначают Семён и Толя. При включении автоматического назначения обновить соответствующий пункт AGENTS.md.

Например, для отчёта по тестовым платежам аналитик сначала публикует пример данных и определение показателей. После этого разработчик интеграции готовит данные, разработчик интерфейса использует тот же пример, а тестировщик готовит контрольные случаи. Если определение показателя меняется, координатор обновляет общую договорённость, помечает затронутые результаты и возвращает их исполнителям. Каждый агент сверяет версию перед сдачей.

**Проверка.** Две роли работают над разными частями одной функции. После изменения общего формата обе части проходят проверку на одной версии данных. При остановке исполнителя другой продолжает с сохранённого результата.

## 5. Возвращать готовое решение

Каждый исполнитель прикладывает результат и собственную проверку. Координатор собирает совместимые изменения в общей рабочей ветке. Тестировщик повторяет сценарий на конкретном коммите и сравнивает результат с исходным запросом. При расхождении координатор возвращает замечание ответственному и повторяет затронутые проверки после исправления.

**Что получает автор команды.** Одно сообщение со ссылкой на рабочую версию или PR, инструкцией запуска, итогами проверки и известными ограничениями. Если сценарий ещё не проходит или исчерпан бюджет попыток, в карточке фиксируются причина остановки и сохранённый результат. Для Тони — воспроизводимый пример, по которому можно снять видео.

## 6. Провести однодневную репетицию

Выберите один бизнес-сценарий и запишите критерий успеха до запуска. Пример команды: «Соберите для владельца магазина сводку по тестовым платежам за день. Покажите, какие платежи требуют внимания, и проверьте итог на контрольном наборе». Конкретный конкурсный кейс команда выберет отдельно.

За день пройдите путь от одной команды до демонстрации. Запишите длительность, стоимость API по ролям, повторные попытки и вмешательства Семёна или Толи. После прогона исправьте самый дорогой или долгий участок и повторите его на том же примере.

**Итог подготовки.** Участник может поставить комплексную задачу со своего аккаунта и получить воспроизводимый результат. В GitHub видно, кто выполнил каждую часть, какое решение использовали агенты и на какой версии тестировщик подтвердил общий сценарий.
