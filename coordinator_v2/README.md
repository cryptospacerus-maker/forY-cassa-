# Coordinator V2

V2 использует отдельный CLI и workflow. Базовый Coordinator MVP продолжает работать через `python3 -m coordinator` и свои workflow. V2 берёт настройки проекта и проверки из доверенного коммита, запускает рабочие роли, формирует кандидата и независимо проверяет этот SHA.

## Запуск без ключей

Из корня ветки V2 выполните:

```sh
docker build -t coordinator-v2-sandbox:local coordinator_v2/sandbox
results="$(mktemp -d)/run"
python3 -m coordinator_v2 --output "$results" \
  --enable execution --enable tests --enable browser --enable mcp
```

Нужны Git, Python 3.11+ и Docker с поддержкой лимитов контейнера. Сеть требуется при сборке образа. Контейнеры проверки запускаются без внешней сети. Флаг `--scenario dependency` включит последовательную передачу от Тёмы к Ксю. По умолчанию используется сценарий с двумя параллельными рабочими ролями. Ответы ролей в обоих сценариях заранее заданы. Python-код, тесты, Chromium и тестовый MCP-провайдер запускаются реально.

| Флаг | Что включает |
| --- | --- |
| `--enable execution` | Рабочая роль может запросить проверку по имени из доверенного профиля. Координатор запускает её на снимке предложения и передаёт структурированный результат. |
| `--enable tests` | Андрюха запускает обязательные автоматические тесты итогового SHA из доверенного набора. |
| `--enable browser` | Андрюха запускает Playwright в новом Chromium. Проверяются фильтр, пустое состояние, сброс и блокирование браузерного запроса вне стенда. |
| `--enable mcp` | Рабочая роль получает разрешённые синтетические данные через тестовый MCP stdio-провайдер. |

Каждый флаг независим и выключен по умолчанию. Workflow `coordinator-v2.yml` позволяет включать их по отдельности при ручном запуске после попадания файла в ветку по умолчанию. CI ветки V2 и PR проверяет комбинацию всех флагов. Workflow CI работает только с синтетическим сценарием, имеет права чтения и прикладывает артефакты.

## Как подключить проект

1. Добавьте по ревью конфигурацию `coordinator_v2/projects/<имя>.json` по примеру [lab.json](projects/lab.json). Укажите каталог предложения и отдельный каталог проверок. У каждой проверки задайте ID, роль, флаг, аргументы Python или Node и тайм-аут. Для проверок Андрюхи можно явно указать владельца исправления.
2. Проверки берутся из доверенного `--base`, а приложение из SHA кандидата. Отведите под приложение только нужную директорию и подготовьте проверяемый базовый каталог. Проверьте команду сначала на синтетических данных. При необходимости соберите доверенный образ с зависимостями проекта и передайте его через `--image`.
3. Для реального Codex предусмотрен отдельный локальный режим `--mode task` с номером Issue, проверкой прав GitHub, разрешённым ключом `CODEX_API_KEY`, моделью `COORDINATOR_MODEL` и явным флагом `--allow-paid`. Используйте его после согласования расхода и в проверенном checkout. CI этого режима не запускает. Перед включением внешнего MCP потребуется отдельно согласованный адаптер и политика доступа. Текущий шлюз запускает только фиксированный тестовый провайдер.

## Результаты и проверка

- `summary.json` содержит статус, базовый и проверенный SHA, backend, флаги, счётчики сессий, переданных байтов, токенов и кеша MCP.
- `events.jsonl` подходит для импорта в панель. Каждое событие имеет `schema_version=2`, `run_id`, UTC-время, последовательный номер, тип события и поля роли, раунда или SHA, когда они применимы. В журнал не включаются промпты, содержимое файлов, сырые ответы MCP и stdout проверок.
- `candidate.patch` и `candidate.pack` записываются после приёмки. В отдельном клоне с базовым коммитом запустите `git unpack-objects < candidate.pack`, затем `git show <sha>` с SHA из отчёта. CLI не публикует ветку или результат в GitHub.

```sh
python3 -m unittest discover -s coordinator_v2/tests -v
COORDINATOR_V2_TEST_IMAGE=coordinator-v2-sandbox:local \
  python3 -m unittest discover -s coordinator_v2/tests -v
```

Вариант без переменной пропускает два теста реального Docker. [Архитектура, ограничения и результаты](REPORT.md)
