# Судья: как работать

Судья — независимый оценщик решения. Не исправляет код и не управляет командой.
Техническая роль `evaluator`, имя в команде «Судья». Один запрос — один вызов LLM.

## Самый простой путь после настройки

В рабочем чате с доступом к репозиторию напишите:

> Судья, оцени задачу №8, коммит <полный SHA>, трек integrator,
> версия требований v1. Манифест evaluation/evidence/manifest.json.

Агент читает профиль, собирает параметры и запускает **только по этой команде**.
Сам текст в обычном чате GitHub ничего не активирует: интеграция чата должна уметь
вызывать Actions. Универсальный доступ — GitHub → Actions → «Судья — независимая
оценка» → Run workflow. Для этого workflow сначала должен быть слит в main.

Первый прогон: `mode=dry-run`. Он проверяет сбор файлов, публикацию и доступы,
но НЕ оценивает конкурсную работу. `mode=live` — отдельный платный запуск.

Результат: комментарий в исходной карточке; в Actions — `judge-report` с
`report.md`, `report.json`, `manifest.json`. Хранение артефактов 30 дней;
важные отчёты заранее сохраняйте в принятую командой постоянную документацию.
Автоматической доставки в произвольный личный чат пока нет.

## Разовая настройка владельцем репозитория

1. Слить проверенный PR в main. Workflow принимает только main.
2. В Repository Settings → Secrets and variables → Actions добавить:

| Тип | Имя | Значение |
|---|---|---|
| Variable | `JUDGE_ALLOWED_ACTORS` | GitHub-логины Семёна и Толи через запятую |
| Secret | `JUDGE_OPENAI_API_KEY` | Отдельный OpenAI API key, не ключ чата |
| Variable | `JUDGE_MODEL` | Доступная модель Responses API со structured outputs |
| Variable | `JUDGE_MAX_USD` | Максимум расчётной стоимости одного прогона |
| Variable | `JUDGE_INPUT_USD_PER_MILLION` | Проверенная цена входных токенов модели |
| Variable | `JUDGE_OUTPUT_USD_PER_MILLION` | Проверенная цена выходных токенов модели |
| Variable | `JUDGE_PRICING_VERIFIED_ON` | Дата проверки тарифов, YYYY-MM-DD |

Для dry-run достаточно разрешённых логинов и прав Actions. Пользователь должен
иметь write/maintain/admin на репозиторий. API-ключ и цены в этой поставке не заданы.
Суточного счётчика расходов в MVP нет; настройте бюджет проекта у провайдера.
Расчёт по байтам консервативный, но не является гарантией фактического счёта;
стоимость reasoning и output учитывается в пределах max_output_tokens выбранной модели.
При изменении тарифов обновите конфигурацию. Автоповторов оплачиваемого вызова нет.

## Подготовка материалов

Создайте в ветке оцениваемого решения `evaluation/evidence/manifest.json`:

```json
{
  "items": [
    {"id":"requirements","path":"PROJECT.md","kind":"requirements","source_sha":"target"},
    {"id":"code","path":"src/app.py","kind":"source","source_sha":"target"},
    {"id":"qa","path":"reports/qa.md","kind":"qa","source_sha":"0123456789012345678901234567890123456789"}
  ]
}
```

`target` означает содержимое того коммита, который передан запуску. Для QA
указывайте настоящий SHA проверенного продукта; файл с другим SHA считается
устаревшим и не может служить основанием баллов. Декларация SHA не доказывает
честность самого QA — сохраняйте логи и команды воспроизведения.

До 30 файлов, каждый до 100 KB, весь пакет до 240 KB; контекст карточки до 100 KB.
Сужайте пакет осмысленно, не обрезайте доказательства молча. Файлы читаются через
Git из заданного SHA, рабочая папка и незакоммиченные изменения не учитываются.
Пути ASCII, внутри репозитория, только обычные файлы. Симлинки запрещены.
Бинарный файл получает SHA-256, но не считается просмотренным. Для слайдов/видео
подготовьте текст/расшифровку; это не заменяет визуальную проверку. URL не скачиваются.
Материалы должны быть без секретов и клиентских персональных данных: отобранный
текст передаётся выбранному API. Модель не имеет инструментов и не выполняет код.

Примерный манифест из поставки содержит только PROJECT.md и README.md — это
технический пример, недостаточный для полной конкурсной оценки.

## Запуск из CLI после слияния

```bash
gh workflow run evaluate.yml --ref main \
  -f issue_number=8 \
  -f target_sha=ПОЛНЫЙ_SHA \
  -f track=integrator \
  -f case_version=v1 \
  -f evidence_manifest_path=evaluation/evidence/manifest.json \
  -f request_id=judge-001 \
  -f mode=dry-run
```

После удачной проверки доставки используйте новый request_id и `mode=live`.
Один request_id в одной карточке резервируется комментарием Actions. Повтор
блокируется до вызова модели. После сбоя изучите предыдущий запуск: запрос к API
мог быть оплачен даже при таймауте. Затем явно задайте новый request_id.
Запуски сериализованы для репозитория; GitHub может отменять ожидающий запуск
при появлении нового в той же concurrency group. Не ставьте массовую очередь.

## Локальный запуск до слияния

```bash
python3 -m pip install -r evaluation/requirements.txt
# GH_TOKEN — доступ на чтение GitHub; не выводите его в терминал/чат.
python3 -m scripts.evaluator.launch \
  --issue 8 --sha ПОЛНЫЙ_SHA --track integrator --case-version v1 \
  --request-id judge-local-001 --output .judge-output/run-001 --dry-run
```

Для live уберите `--dry-run` и задайте в окружении `OPENAI_API_KEY`, `JUDGE_MODEL`,
`JUDGE_MAX_USD`, обе цены и дату проверки тарифов. Локальный запуск не публикует
результат: откройте выведенный путь report.md. Для нового прогона — новая папка.
Локальная команда требует доверенного checkout кода Судьи; не запускайте её
из произвольной ветки конкурсной работы. Целевые Git-объекты должны быть скачаны.

Низкоуровневая команда `scripts.evaluator.run --request ... --context ...` принимает
JSON по evaluation/schemas/input.json. `--response-file` предназначен только для
тестов: такие отчёты всегда имеют статус fixture, а не реальный вердикт.

## Что означает отчёт

- `reviewed`: все критерии рассмотрены; это предварительная оценка, не приёмка QA.
- `partial`: часть критериев без данных, итог не нормируется до 100.
- `blocked`: ошибка входа, доступа, бюджета, API или схемы; причины в отчёте.
- `dry_run`: только техническая проверка, баллов нет.
- `fixture`: офлайн-проверка формата на подготовленном ответе.

Ноль — доказанное отсутствие результата. `null` — недостаточно данных.
За предложенные, но ещё не сделанные улучшения баллы не начисляются.
Команда выбирает рекомендации; Игорёк назначает работу, Андрюха проверяет
исправленный SHA. Повторная оценка только по отдельной команде.
