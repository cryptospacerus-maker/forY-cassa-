# Реализация и приёмка

## Этапы

1. **Проектирование сейчас.** Согласовать протокол и матрицу полномочий в #22. Проверить на исторических карточках и синтетических примерах чтение статуса, формирование задачи, сверку результата и работу с дублями. Сессии используют ссылки на GitHub и существующие инструменты. Эта поставка содержит документацию.
2. **Ручная инфраструктурная приёмка.** После появления VPS пройти приёмку #19 и действующие [критерии V3](../coordinator_v3/ACCEPTANCE.md). Проверить права обеих сессий, идентичность издателя, три Worker, состояние операторского контура и GitHub-уведомление. Живой тест требует отдельного допуска. Владелец запуска и оператор зафиксированы в Issue.
3. **Реализация Management MVP после утверждения проекта.** Добавить тонкий операторский шлюз и журнал принятия рядом с V3, с единым маршрутом для мутаций. Для проверки чтения и нормализации команд использовать фикстуры. Перед изменением интеграции проверить, что существующий V3 CLI достаточно стабилен. Состояние и роли берутся из V3, требования и результаты — из GitHub. Платный API не нужен.
4. **Автоматизация после приёмки ручного маршрута.** [Issue №20](https://github.com/cryptospacerus-maker/forY-cassa-/issues/20) покрывает watcher и cursor, GitHub App tokens, durable publication outbox, мониторинг. Будущий watcher проходит тот же допуск и дедупликацию между авторами, без прямой выдачи Worker. Затем панель #6/#7 читает безопасные статусы, отдельно проверяется задержка и доступ.

## Критерии приёмки

| Сценарий | Проверяемый результат | Этап |
| --- | --- | --- |
| Семён и Толя открывают одну карточку из двух личных сессий | Совпадают Issue, версия, SHA и ссылки на решения. Каждая сессия показывает автора и источник | Сейчас, на исторических данных |
| Для каждого выражения есть команда и ошибка | 8 команд имеют источник, права, действия и результат. Неоднозначный объект требует выбора | Сейчас |
| GitHub или хост недоступен | Возвращаются последний подтверждённый факт, источник и время. Запись не выполняется, живое состояние неизвестно | Сейчас и фикстуры оператора |
| Два участника одновременно просят одну версию задачи | Через шлюз создаётся один канонический запрос и один run. Повтор между авторами получает его ссылку. Тестировать конкурентно и после рестарта | Ручной маршрут репетируется сейчас, техническая гарантия проверяется после реализации шлюза |
| Две задачи пересекаются по файлам | Вторая ждёт явной развязки либо подтверждённой зависимости. Непересекающиеся области остаются независимыми | Шлюз |
| Неизвестный исход импорта или публикации | Состояние остаётся зарезервированным. Повтор сверяет идентичный запрос и маркер, скрытых повторных POST или запусков нет | Ручной V3 и шлюз |
| Чужие права, отмена, просроченный lease | Неавторизованному участнику отказывают. Отмена точно адресована run. Выданный шаг с неизвестным исходом ожидает сверки | Ручной V3 |
| Старый результат или неполные тесты | Отчёт на чужой SHA не принимает текущий кандидат. Недоступный тест или evidence отмечается отдельно | Сейчас |
| Завершение и передача | В GitHub один опубликованный результат с нужным SHA, ссылкой и @упоминанием инициатора. Второй участник видит общий Issue | Ручной V3 |
| Независимая оценка | Судья привязан к полному SHA, треку и версии. Отчёт валидируется, изменения и назначения делаются отдельным действием | Действующий контур Судьи |
| Автоматическая доставка и панель | Повтор страницы, edit/delete, рестарт и потеря ответов не дублируют run или итог. Панель показывает время и источник без закрытых полей | №20 и отдельная интеграция панели |

## Решения для согласования

- Назначить оператора пилота и одного владельца запуска на карточку. Утвердить, кто вправе передавать владение и запрашивать отмену.
- Утвердить область конфликтов, формат связи Issue с run и минимум полей для статуса. Предлагаем начать с обычных ссылок и коротких записей в GitHub.
- Утвердить техническую сериализацию допуска на стороне оператора и её обязательность для будущего watcher. JSON текущего `status` не публикуется целиком.
- Отдельно решить, нужна ли панели вторая стадия с живыми статусами и какой срок свежести достаточен. До этого панель использует только опубликованные данные GitHub.
