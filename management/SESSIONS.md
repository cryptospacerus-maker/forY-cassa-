# Работа из личных сессий

## Текст для своего чата ChatGPT

> Помоги мне принять решение по проекту Хакатон ЮКассы. Я передам ссылку на GitHub Issue и короткий статус. Уточни цель, версию требований и способ проверки, обозначь нерешённые вопросы. Сформулируй одну следующую команду для моего Codex. Если GitHub недоступен, опирайся на переданную выжимку и явно отделяй предположения от фактов. Пока я обсуждаю задачу, держи результат как черновик.

## Текст для своей сессии Codex

> Работай с cryptospacerus-maker/forY-cassa-. Прочитай AGENTS.md и PROJECT.md из main, связанную карточку и её комментарии, активные смежные задачи и актуальные SHA. Выполни одну явно указанную команду по management/COMMANDS.md. Используй мою подтверждённую GitHub-личность и действующие права. Перед записью проверь каноническую карточку, текущую версию, владельца и дубли. Для живого действия V3 соблюдай допуск пилота и обращайся к назначенному оператору. Верни ссылку на Issue, краткий статус с источником и временем и следующий шаг с ответственным. Полные логи и секреты в общий Issue или другой чат не переноси.

До принятия документа участник может дать Codex ссылку на draft PR как исходный материал для проверки протокола. Канонические инструкции проекта продолжают читаться из main. При недоступности GitHub сохранить локальный черновик, отметить время имеющейся выжимки и отложить запись до повторной проверки.

### Короткая выжимка между сессиями

`[Issue] · [версия] · [фактический статус + ссылка] · [run/SHA, если есть] · [блокировка или следующий ответственный]`

Семён и Толя читают одну карточку, даже если обсуждают её в разных чатах. Ссылка на Issue или итоговый комментарий заменяет передачу полного отчёта. Для личного чата без GitHub достаточно этой строки. Публикация идёт в GitHub, вернуться в существующий чат ChatGPT можно вручную.

## Сценарий A. Подготовка задачи до приёмки V3

1. Семён обсуждает в ChatGPT критерии синтетического каталога. Чат возвращает три поля карточки и предложение `Сформируй следующую задачу по #18`.
2. В своей сессии Codex Семён просит `Передай задачу команде по #18 в режиме подготовки`. Codex находит существующий Issue, проверяет, кто выступит инициатором, и фиксирует согласованное уточнение, если это прямо поручено и права позволяют.
3. Ответ Codex — ссылка на #18, версия, `prepared`, «следующий ответственный — владелец задачи после инфраструктурной приёмки». Команды запуска и run ID пока нет.
4. Толя открывает #18 из своей сессии и спрашивает `Покажи статус команды`. Он получает тот же опубликованный факт. Для обсуждения следующего шага Семён возвращает в ChatGPT одну строку со ссылкой.

## Сценарий B. Ручной пилот после приёмки V3

1. Семён подтверждает работу и становится владельцем после принятия его команды по #18. Толя как оператор сверяет версию, готовность окружения и отсутствие конфликтов. Семён оставляет `/coordinator-v3 catalog-acceptance`. Оператор принимает точный comment ID, один раз выполняет `ingest` и фиксирует run.
2. Если Толя тоже просит `Передай задачу команде по #18`, оператор находит существующий run. Логин автора, ключ и привязка к комментарию сохраняются, второй запуск не создаётся.
3. На вопрос `Что сейчас делает каждый агент?` сессия показывает наблюдаемое состояние шагов. Например, Тёма — `leased`, Ксю — ждёт зависимости, Андрюха — ещё не назначен. Состояния берутся из свежего отчёта оператора.
4. После QA оператор сверяет точный SHA и вызывает штатный `publish`. GitHub Issue получает итог с @упоминанием Семёна. Толя открывает тот же итог.
5. В личном Codex Толя просит `Проверь результат задачи №18 по SHA из отчёта`. Codex называет проверенный SHA и отдельно перечисляет самостоятельно проверенное и прочитанное из CI. Семён возвращает ссылку и вердикт в ChatGPT и обсуждает следующую задачу.

## Сценарий C. Замечания, исправление и отмена

1. Толя обнаруживает, что проверка пустой категории не покрыта. Команда `Передай замечания на исправление` создаёт согласованную связанную карточку или находит существующую. В неё записываются SHA, ожидаемое/фактическое, тест и область файлов. Для исправления результата Семёна требуется его поручение.
2. Если исходный run ещё активен, внешний запуск ждёт решения владельца и окончания либо отмены. Встроенное исправление, принятое самим V3 по итогам QA, проходит внутри исходного run.
3. Если Семён как владелец явно просит отменить run, оператор вызывает `cancel` для точного ID. Получатель видит «отмена подтверждена координатором, один выданный шаг требует сверки» при наличии `needs_review`. Владелец Worker подтверждает фактический исход, оператор фиксирует его через `review-job`.
4. При технической аварии Толя может остановить run сам, записав причину и уведомив Семёна. Только после сверки можно выдавать новую версию. Повтор команды со старым ключом возвращает историю исходного запуска.

## Сценарий D. Толя инициирует вторую задачу и передаёт результат

1. Толя сам ставит отдельную задачу. После принятия его команды Толя владеет этим run как инициатор и выполняет операторские действия в рамках пилота. Семён читает статус и предлагает замечания.
2. Толя публикует общий итог с доказательствами. В GitHub оба видят тот же SHA, а упоминание получает Толя как фактический инициатор.
3. По явно согласованному решению Толя передаёт Семёну следующий шаг. В Issue фиксируются результат, ссылка, SHA, проверка, следующий шаг и получатель. Автор завершённого run остаётся Толей. Если Семён инициирует новую работу, новый run принадлежит Семёну.

## Сценарий E. Независимая оценка и следующий шаг

1. Толя просит `Судья, оцени результат задачи №18, SHA …, трек integrator, версия требований …`. Предусмотренная сессия использует действующий профиль и собирает пакет по указанной версии.
2. Судья отдаёт валидированный отчёт с доказательствами и рекомендациями. По явному поручению он публикуется в Issue, сессия возвращает ссылку и короткий итог.
3. Семён обсуждает рекомендации в своём ChatGPT. Принятое решение фиксируется в GitHub. `Сформируй следующую задачу` готовит черновик по принятой рекомендации. Выдача в работу выполняется отдельной командой через назначенного владельца.
