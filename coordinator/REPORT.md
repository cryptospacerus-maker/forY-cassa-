# Coordinator MVP. Архитектура и испытания

## Как проходит задача

1. **Подготовка.** GitHub Actions получает номер Issue, режим и ключ запроса. Инициатор определяется по `github.actor`. Координатор сверяет логин со списком команды, проверяет права GitHub и фиксирует запуск в Issue. Ключ включает репозиторий, Issue, инициатора, режим и запрос.
2. **Контекст.** Снимок включает карточку и последние комментарии, до четырёх связанных карточек, `AGENTS.md` и `PROJECT.md` по исходному SHA. В режиме task аналитик видит ограниченный список путей. Исполнитель получает содержимое отведённых файлов и результаты своих предшественников. Сверки выполняются перед работой, передачей в QA и публикацией.
3. **План и исполнение.** Игорёк определяет критерии и зависимости. Координатор проверяет план и сам выбирает последовательность запусков. Независимые поручения выполняются одновременно в отдельных сессиях. Области записи разведены по путям. Модели возвращают структурированный JSON, а Git-коммит создаёт координатор в отдельном индексе.
4. **Приёмка.** Андрюха получает данные непосредственно из проверяемого Git-коммита. Режим demo также независимо проверяет JSON с контрольным результатом. Если требуется исправление, координатор передаёт дефект владельцу и повторно проверяет новый SHA. Итог привязан к проверенному SHA.
5. **Состояние и доставка.** После каждой сессии состояние обновляется атомарно. Actions сохраняет его отдельным артефактом, который исходный запуск может перечитать при повторе. Публикация выполняется отдельной задачей с правами записи. Она восстанавливает Git-коммит, сравнивает его с принятым SHA, создаёт ветку результата и оставляет один отчёт с упоминанием инициатора.

Сессии Codex используют временные рабочие каталоги и ограниченную конфигурацию CLI. Вызовы shell, MCP, поиск, плагины, хуки и вложенные агенты отключены. У сессий есть API-авторизация, а GitHub-токен им не передаётся. Артефакты содержат результаты и ответы ролей, поэтому видимость репозитория и доступ к Actions определяют круг читателей. Ветка результата создаётся отдельным заданием. Операции с главной веткой и управление workflow в контракт исполнителей не входят.

## Проверка критериев

| Критерий | Статус | Фактическая проверка |
| --- | --- | --- |
| Одной командой запускается координатор | Частично проверено | CLI запущен на локальном примере и на реальном открытом Issue #12 через GitHub API. Живой `workflow_dispatch` требует workflow в `main`. |
| Исполнители вызываются автоматически | Частично проверено | Автотесты проверяют планирование и вызовы ролей с подменёнными ответами. Для живого Codex необходимы API-ключ и модель. |
| Результаты передаются между агентами | Частично проверено | Передача файлов и результата предшествующей роли подтверждена в автотесте. |
| Андрюха независимо проверяет конкретный коммит | Частично проверено | Создавались реальные Git-коммиты, проверялись их SHA и содержимое. Роль тестировщика подменялась. Для demo выполнялась реальная детерминированная проверка JSON. |
| Дефект отправляется на исправление | Частично проверено | Детерминированная проверка отклонила первый коммит. Следующий ответ исполнителя привёл к новому коммиту, который прошёл проверку. Ответы агентов подменялись. |
| Формируется итоговый отчёт | Проверено | CLI сформировал dry-run с данными реальной карточки. Генерация итогового комментария проверена автотестом. |
| Инициатор получает уведомление | Частично проверено | Автотест проверяет формирование одного комментария с упоминанием инициатора. Получение уведомления в аккаунте ещё требуется проверить. |
| Повторный запуск не создаёт неконтролируемые дубликаты | Частично проверено | Проверены повтор завершённого состояния, восстановление по сохранённому ответу, резервирование и защита от повторного комментария. Настоящий повтор GitHub Actions требует развёртывания workflow. |
| Поддерживаются два рабочих аккаунта | Частично проверено | GitHub API подтвердил права `write` для обоих логинов. Локально авторизован и проверен один аккаунт. |
| Существующие компоненты продолжают работать | Частично проверено | Изменения изолированы в `coordinator/` и новом workflow. Код панели, пилота, «Судьи» и действующей проверки сайта отсутствует в diff. Их живые проверки ведутся отдельно. |

Локально прошли 12 автоматических тестов и `actionlint`. Контрольный пример вынесен в [Issue #13](https://github.com/cryptospacerus-maker/forY-cassa-/issues/13). GitHub API дал HTTP 403 при чтении настроек Actions, переменных и секретов. Наличие ключа в репозитории не подтверждено. В локальной среде API-ключ для платного запуска отсутствовал.

## Оставшиеся ограничения

- Для запуска из GitHub нужен workflow в `main`, репозиторные параметры и ключ доступа к API. Живую приёмку следует выполнить командами из README, последовательно под двумя логинами.
- Восстановление использует последний опубликованный артефакт. При жёстком обрыве до его загрузки сессии, прошедшие после доступной контрольной точки, могут повториться в исходном запуске. Артефакт хранится семь дней.
- Режим task поддерживает до двух рабочих ролей, текстовые изменения и ограниченную проверку по содержимому. Запуск сгенерированного кода или реальные внешние интеграции требуют отдельной доверенной проверки. Разрешённые каталоги задаются независимо от Issue.
- Порог токенов проверяется перед следующей группой сессий. Стоимость по заданным тарифам является оценкой, а полнота расхода зависит от полученных событий `turn.completed`.
- Возврат в исходный личный чат Codex не подтверждён. В официальной документации SDK описано возобновление сессии, которой управляет интеграция. Документация Work описывает уведомления для поддерживаемых событий PR в аккаунте Work. Для публикации сообщения в произвольный исходный чат Codex подходящий интерфейс в проверенных источниках не найден. MVP доставляет итог через GitHub Issue.
