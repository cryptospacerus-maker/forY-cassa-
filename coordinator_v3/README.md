# Coordinator V3

V3 связывает команду в GitHub Issue с координатором и тремя средами Codex CLI под контролем владельцев. SQLite хранит задания, результаты, версии требований, историю доставки и доказательства QA. Worker сам забирает задание и использует локальную сессию. V3 переиспользует маршрутизацию, проверку файлов и QA V2. Доставка результатов использует те же проверки разрешённых файлов и точного SHA с отдельной веткой и маркером отчёта.

## Офлайн-проверка

Из корня репозитория с Python 3.10+ и Git выполните. Зависимости Судьи установите внутри venv:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r evaluation/requirements.txt
python3 -m unittest coordinator_v3.test_spike coordinator_v3.test_v3 coordinator_v3.test_hardening -v
python3 -m unittest discover -s coordinator/tests -v
python3 -m unittest discover -s coordinator_v2/tests -v
python3 -m unittest discover -s tests -v
```

Интеграционный тест запускает HTTP на loopback, три Worker, настоящие SQLite и Git и имитаторы CLI, GitHub и QA. Скрипт-имитатор CLI отдельно проверяет порядок флагов, stdin, JSONL, итоговый файл, тайм-аут и explicit resume. Браузер и контейнер в регрессии V2 требуют локального образа из `coordinator_v2/sandbox` и `COORDINATOR_V2_TEST_IMAGE`; точный CLI-тест V1 требует `codex-cli 0.172.0`.

## Координатор и приём задач

Включайте живой контур после закрытия блокеров из [приёмки](ACCEPTANCE.md). Координатору нужны Python 3.10+, Git, утверждённый профиль QA и локально собранный образ V2 Sandbox. Настройте bare Git store, read-only код, systemd, HTTPS и служебные права по [инструкции развёртывания](DEPLOYMENT.md). Перед запуском сверяйте доступность Git-объектов доверенного `main` в checkout. Рабочий каталог состояния должен иметь режим 0700. Для сетевого запуска опубликуйте через HTTPS-прокси только четыре POST-эндпоинта `/v1/{register,claim,heartbeat,complete}`. Сам сервер слушает 127.0.0.1. Настройте отдельные токены и непротиворечивые алиасы в закрытом JSON по схеме:

```json
{
  "tolya": {"account": "tolya-owner", "token": "<секрет Толи>"},
  "semen": {"account": "semen-owner", "token": "<секрет Семёна>"},
  "third": {"account": "third-owner", "token": "<секрет третьего владельца>"}
}
```

Создайте каждый токен отдельно через `python3 -c 'import secrets; print(secrets.token_urlsafe(32))'`. Файл credentials храните с правами 0600. Передайте каждому владельцу только его токен через закрытый канал. Для ротации замените соответствующий токен в JSON и перезапустите сервер.

```bash
umask 077
mkdir -p "$PWD/../v3-state"
export COORDINATOR_ACTORS='<логины допущенных участников через пробел>'
V3_STATE="$PWD/../v3-state"
python3 -m coordinator_v3 --state "$V3_STATE" serve \
  --credentials "$V3_STATE/workers.json" --reader-token "$V3_STATE/github-reader" --advance-github
```

Без `--advance-github` сервер не читает GitHub при обработке очереди. Флаг запускает периодическую обработку уже принятых задач. Обе команды ниже запускаются из того же checkout и с тем же каталогом состояния. REST принимает отдельные файлы токенов чтения и публикации. Git push использует credential helper служебного издателя.

```bash
# Участник пишет в открытой карточке: /coordinator-v3 catalog-acceptance
# Оператор передаёт точный ID комментария и ID утверждённого локального образа.
python3 -m coordinator_v3 --state "$V3_STATE" ingest \
  --issue 18 --comment "<числовой ID>" --project lab --reader-token "$V3_STATE/github-reader" \
  --features tests browser --image "<sha256:...>"
python3 -m coordinator_v3 --state "$V3_STATE" status

# После завершения, с полномочиями назначенного издателя.
python3 -m coordinator_v3 --state "$V3_STATE" publish \
  --run "<ID запуска>" --publisher "<логин издателя>" --publisher-token "$V3_STATE/github-publisher"
```

В этом пилоте импорт команды и публикация остаются явными действиями оператора. Автоматическое обнаружение комментариев, выпуск и ротация токенов GitHub App и настройка работающей HTTPS-инфраструктуры относятся к этапу приёмки. Для проверки одного шага обработки есть `advance --github --reader-token <файл>`. Допуск требует точной команды в открытом Issue, разрешённого инициатора и действующего права записи. Используйте новый request key для изменённых требований только после сверки предыдущего запуска.

## Подключение Worker

| Владелец | `--id` | Алиас в примере | Роли |
| --- | --- | --- | --- |
| Толя | `tolya` | `tolya-owner` | Тёма |
| Семён | `semen` | `semen-owner` | Ксю |
| Третий владелец | `third` | `third-owner` | Игорёк и Андрюха |

У каждого владельца свой каталог состояния 0700, файл токена 0600 и свой checkout проверенного коммита V3. Владелец задаёт `V3_ROLE`, `V3_WORKER`, `V3_ACCOUNT` и `V3_STATE`. Роли для входа — `developer` у Толи, `interface` у Семёна, `analyst` и `tester` последовательно у третьего владельца.

```bash
umask 077
mkdir -p "$V3_STATE/codex/$V3_ROLE"
CODEX_HOME="$V3_STATE/codex/$V3_ROLE" codex login
CODEX_HOME="$V3_STATE/codex/$V3_ROLE" codex login status
codex --version  # для этого пилота: 0.172.0
codex exec --help
codex exec resume --help
codex sandbox -c 'sandbox_mode="read-only"' /usr/bin/true
```

Для `analyst` и `tester` третий владелец выполняет процедуру входа в каждый каталог сам, через свой аккаунт. Операционная система может хранить учётные данные общего аккаунта в своём хранилище, проверяйте выбранный аккаунт в каждом профиле. Алиас подтверждает согласованную привязку Worker, а `login status` подтверждает способ входа. У Игорька и Андрюхи логически раздельные `CODEX_HOME`, рабочие каталоги и явная привязка resume. При общем UID процесс владельца может читать оба каталога. Для защиты от скомпрометированного локального процесса потребуются отдельные OS identities, границы файловой системы и изоляция хранилища credentials. Уникальность аккаунтов подтверждают владельцы, поскольку алиас сам по себе её не доказывает. Каждая новая задача получает новый thread; доработка сохраняет локальный ID только в той же роли и задаче. Git и API-учётные данные координатора в процесс модели не передаются.

После отдельного согласования живого запуска владелец в обычном Terminal выполняет:

```bash
python3 -m coordinator_v3 --state "$V3_STATE" worker \
  --id "$V3_WORKER" --account "$V3_ACCOUNT" --url "$V3_COORDINATOR_URL" \
  --token-file "$V3_STATE/worker.token" --enable-live-cli
```

## Восстановление

В `status` видны все три Worker и задания. Невыданное задание ждёт своего Worker. Выданное задание с истекшей арендой переходит в `needs_review`, а результат по старой аренде отклоняется. Worker после рестарта сначала доставляет сохранённый результат. При действующей аренде повторная отправка того же результата идемпотентна. После тайм-аута или сбоя сверяйте локальное состояние Worker и Usage владельца. После снятия причины `resume-worker <id>` разрешит этому Worker брать другие задания. Старый выданный шаг повторно не исполняется. `cancel <run>` отзывает допуск и аренды. Для неоднозначного исхода оператор проверяет у владельца, что процесс завершён, и фиксирует `review-job <id> confirmed_stopped|confirmed_finished|outcome_unknown`. Пока исход неизвестен, снять паузу Worker нельзя.

При остановке публикации со статусом `posting` повтор `publish` ищет комментарий служебного актёра по уникальному маркеру. Если маркер не найден, сверьте историю доставки с GitHub перед ручным решением. SQLite и checkout с проверенными Git-объектами нужно сохранять вместе. SQLite в WAL-режиме копируйте через SQLite Backup API или на остановленном сервисе. Worker хранит свой SQLite и каталоги Codex только у владельца.

## Usage

В закрытой среде координатора используйте `report <run>` для чтения итоговых данных. Хранятся только наблюдаемые числовые счётчики завершённых CLI-вызовов и отметка resume. Отсутствующие данные записываются как `null`, подтверждённый ноль сохраняется. Счётчики разных вызовов не складываются: на resume CLI может представлять накопленные данные. История операций владельца остаётся источником сведений о денежных списаниях.
