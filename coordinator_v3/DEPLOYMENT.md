# Предложение по развёртыванию V3

Для координатора и SQLite стартовая инженерная оценка — 2 vCPU, 4 GB RAM и 30 GB SSD. Предложенные Ubuntu 24.04 LTS x86-64, 4 vCPU, 8 GB RAM и 80 GB SSD достаточны как стартовая конфигурация VPS координатора. Docker и Chromium при необходимости запускаются последовательно на отдельном QA-воркере. Реальная пиковая память и диск требуют измерения. Германия — допустимый вариант размещения координатора при соответствии требованиям команды к региону и доступу. Регион VPS не меняет географию и правила авторизации владельцев. Сервер в этом этапе не разворачивался.

## Координатор

1. После согласования создать отдельного пользователя `coordinator` без доступа к Docker socket и личным директориям. Установить обновления и пакеты `git python3 python3-venv ca-certificates` через Ubuntu APT. TLS-терминацию поручить согласованному прокси. Выставить наружу только HTTPS для сервиса. Администрирование — SSH ключами с ограничением доступа команды.
2. Размещать код по утверждённому SHA в `/opt/coordinator-v3` только на чтение. Состояние и аудит — `/var/lib/coordinator-v3/{queue.sqlite,audit/}`. Учётные данные GitHub App и worker — отдельно от Git под правами сервиса, резервные копии SQLite с согласованным сроком хранения. Личных авторизаций Codex на этом сервере нет.
3. GitHub App ставится только на этот репозиторий. Для чтения карточек и комментариев и записи итогов нужны Issues read/write, для публикации ветки Contents read/write, Metadata read. Pull requests write нужен только если включим открытие PR. Токен установки краткоживущий. Право записи участников проверяется по применимому GitHub API, при отказе доступ закрывается до проверки. Права приложения не должны давать обход защиты main. [Токены установки](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)
4. После реализации постоянного entrypoint включить systemd unit с `User=coordinator`, `WorkingDirectory=/opt/coordinator-v3`, `Restart=on-failure`, `RestartSec=5`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `ReadWritePaths=/var/lib/coordinator-v3`. `ExecStart` указывает на проверенный entrypoint из будущей ветки реализации. Включение — `sudo systemctl daemon-reload`, `sudo systemctl enable --now coordinator-v3`. Проверка — `systemctl status coordinator-v3` и `journalctl -u coordinator-v3`. Прототип не является entrypoint для сервиса.
5. Перед включением доступа сверить защиту `main`, работу короткоживущего токена и акторов. После перезапуска SQL-состояние загружается, просроченные выданные задания приостанавливаются до сверки. Отозвать worker credential на VPS и остановить локальный worker при отключении исполнителя. Владелец отзывает свою CLI-авторизацию локально через `codex logout`. Для снятия доступа самого VPS удалить установку приложения либо отозвать его ключ.

## Исполнители

Толя поднимает worker Тёмы, Семён worker Ксю, третий владелец — worker для раздельных ролей Игорька и Андрюхи. Каждый ставит официальную стабильную CLI, сверяет версию и проверяет Usage своего плана. Каждый сам запускает `codex login` либо `codex login --device-auth` при доступности device flow для аккаунта, затем `codex login status`. Ключи API и данные авторизации не передаются координатору. [Авторизация Codex](https://learn.chatgpt.com/docs/auth)

Worker использует отдельный локальный служебный профиль/пользователя под контролем владельца и раздельные каталоги `work/<role>/<job>` и `sessions/<role>`. Для третьего владельца — отдельные каталоги и ID, один одновременный turn на аккаунт на пилоте. Worker проверяет полномочия и подпись заданий по назначенному ключу, держит авторизацию в хранилище владельца, передаёт только статус и разрешённый результат. Отдельный QA runner выполняет только утверждённые команды на кандидат SHA. Послепилотную настройку мониторинга и ротации ключей согласовать по фактическим результатам.
