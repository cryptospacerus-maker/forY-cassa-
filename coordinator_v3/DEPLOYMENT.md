# Подготовка пилота Coordinator V3

До завершения финансовой сверки, повторного ревью и согласования доступа используйте только офлайн-проверки. Для пилота координатор работает на Linux с systemd, а Worker запускаются в средах владельцев. Тесты Git и SQLite не требуют GitHub-токенов или Codex.

## Подготовка сервиса и проверка C2

1. Установите Git, Python 3.10+, systemd и nginx. На согласованном Linux-хосте подготовьте выделенный rootless Docker для пользователя `coordinator`. Сокет rootful Docker не предоставляйте. Перед настройкой ingress сверьте поддерживаемые ограничения CPU, памяти и PID. Используйте [заданный образ V2](../coordinator_v2/sandbox/Dockerfile) и сохраните его итоговый локальный `sha256:` ID.
2. Разместите проверенный checkout по точному SHA в `/opt/coordinator-v3`, владелец root, код с доступом на чтение для сервиса. Администратор создаёт сервисного пользователя и приватный каталог `/var/lib/coordinator-v3` с режимом 0700. От его имени и с `umask 077` подготовьте bare Git store:

   ```bash
   git init --bare /var/lib/coordinator-v3/git
   git --git-dir=/var/lib/coordinator-v3/git remote add origin \
     https://github.com/cryptospacerus-maker/forY-cassa-.git
   git --git-dir=/var/lib/coordinator-v3/git fetch --no-tags origin \
     refs/heads/main:refs/remotes/origin/main
   ```

   Убедитесь, что каталог `git/` имеет режим 0700. V3 передаёт `--git-dir` к этому хранилищу для чтения и записи объектов и refs. SQLite и WAL находятся под `/var/lib/coordinator-v3`, временные файлы unit — в `/run/coordinator-v3`. Код и Git store могут обновляться независимо. Импорт сверяет адреса origin для чтения и записи и подгружает недостающий проверенный main.
3. В `/etc/coordinator-v3/settings` задайте `V3_BASE_SHA` (доверенный main), `V3_QA_IMAGE`, `DOCKER_HOST` (сокет rootless Docker) и `COORDINATOR_ACTORS` (список логинов через пробел, заключённый в кавычки). Подготовьте `workers.json` и `github-reader` с правами 0600 для systemd LoadCredential. Скопируйте [unit](deploy/coordinator-v3.service) и проверьте его через `systemd-analyze verify`.
4. До подключения Worker выполните preflight под тем же UID и ограничениями, что в unit. Он запускается как `ExecStartPre`. Для отдельного прогона скопируйте unit под именем `coordinator-v3-preflight.service`, замените основную `ExecStart` командой из `ExecStartPre`, удалите исходную `ExecStartPre`, добавьте `Type=oneshot` и уберите `Restart=on-failure`. В журнале должны быть подтверждены SQLite/WAL, создание и чтение синтетического Git-кандидата/refs, приватный временный каталог и реальный Python/браузерный запуск из закреплённого Docker-образа. Незакреплённый или недоступный образ блокирует старт по unit.
5. Проверьте отдельные служебные полномочия. Reader получает только нужное чтение Issues, коммитов и прав инициатора. У publisher должна быть возможность писать Issues и только ветку результата. `publish` сверяет `/user` с ожидаемым логином перед записью. Для пилота используйте отдельного ограниченного служебного пользователя с пользовательским токеном и его настроенный Git credential helper. Сверьте фактический Git-аккаунт и защиту `main` с администратором. Файлы токенов храните с правами 0600. Выпуск и ротация краткоживущих GitHub App installation tokens находятся за границей этого пилота.

## HTTPS и диагностика

Используйте [шаблон nginx](deploy/nginx.conf) с сертификатом для своего hostname. До старта выполните `nginx -t`, затем проверьте из среды владельца доверенную цепочку TLS, доступность только четырёх POST-эндпоинтов, ответы для чужого и отозванного токена, отказ для тела свыше 128 КиБ и срабатывание лимитов. Backend слушает loopback. Nginx буферизует запрос и ограничивает время чтения, размер, запросы и соединения. Backend проверяет Bearer до чтения JSON и ограничивает число обработчиков. Для ротации измените только нужный токен и перезапустите unit. Сохранённые аренды остаются действительными до своего deadline.

`status` показывает `awaiting_github`, `ready`, состояния Worker и шагов. Допуск действителен до 30 секунд с начала последней полной сверки. При известной недоступности GitHub отзыв выполняется в SQLite. Уже выданный turn подчиняется аренде и отмене. Сервис ограничивает частоту запросов, число активных запусков и страницы REST. При превышении ограничений выдача ждёт следующей успешной сверки. Следите за возрастом допуска, `needs_review`, свободным местом и состоянием `posting`. В пилоте сроки хранения согласуются вручную, автоматического удаления истории нет.

## Резервная копия и восстановление

Остановите сервер и команды оператора. Сделайте закрытую копию SQLite через `sqlite3 ... ".backup /защищённое-место/queue.sqlite"` и копию всего bare Git store с refs и журналами из каталога состояния. Redispatch-данные из этого состояния нельзя переносить на другую активную копию сервиса. Worker отдельно сохраняет локальный SQLite. Личные каталоги Codex и авторизация остаются в средах владельцев.

Восстанавливайте SQLite и Git из одного окна в закрытый каталог под тем же UID. Выполните `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, `git fsck --full`, preflight и `status`. При старте допуски отзываются. У просроченных аренд проверяйте локальный исход, затем фиксируйте итог через `review-job`. Отсутствие маркера комментария при `posting` требует ручной сверки. Перед повторной эксплуатацией проверьте процедуру восстановления на отдельном офлайн-каталоге.

При обновлении с `e4c4a86` новые таблицы создаются автоматически. Ранее импортированные pending-запуски, для которых отсутствует ID исходной команды, блокируются после сверки. Сначала разберите их аренды и состояние, затем используйте новый request key для новой принятой задачи. Существующие результаты остаются в истории.
